Foundations Analysis

theSystem's core loop does not exist yet. The orchestrator is a three-line stub, while the tooling around it is polished. Build one rough end-to-end run first, and let verification, not writing, shape the design.

Sources: the theSystem repo, the earlier legacy-workspace attempt, and the Hermes (default, implementer, reviewer, kanban), Codex and Claude Code history. verified marks evidence checked directly against files or databases. Other evidence comes from the research pass over session history. The twelve tickets in .scratch/foundations/issues/ put these conclusions into practice.

2What to keep

  • Deterministic control flow. "No LLM decides control flow inside the orchestrator" fixes the legacy-workspace draft, where --attempt-limit silently bypassed the documented retry policy. verified
  • Rules need an incident. Prevents: is a scarcity mechanism. It stops rule bloat, the knowledge-side version of abstraction bloat.
  • The docs ladder (drop, rule, ADR, ledger, wiki). It makes keeping a fact expensive now that producing one is free.
  • Bright lines over judgement calls. The comment rule was exploited while it allowed a judgement call. The rewrite named the incident and removed the judgement.
  • Deterministic gates worked every time you built one: the surface-preservation sentinel, the comment pre-commit hook, the rule-field hook.
  • The human stays in control during bring-up. Single-pass runs, no auto-fix loop. That is right until the loop can be measured (3.2).
  • Reviewer independence. Fresh-context reviewers caught what implementers rationalized.

3The revaluations

Each one comes from your own evidence. It names the old practice, what changed, what your history shows, the new practice, and the tickets that act on it.

3.1

Build the loop before the furniture

Old practice
Build each infrastructure piece well, one at a time, because rewriting is expensive.
What changed
Rewriting is cheap. The expensive thing is not knowing whether the whole system works.
Evidence
orchestrator is 3 lines and every role list in orchestrator.yaml is empty. bootstrap is 341 lines, with a spinner checklist. Memory review is 717 lines plus an external LLM judge, and its ASCII card took about 20 revision turns. A working-ish orchestrator with tests sits uncommitted in legacy-workspace, and it was re-derived in a 7-hour interview. verified The INST-142 rehearsal hit four infra failures and never attempted the feature itself.
New practice
Build a rough end-to-end run on a toy project before polishing any component. Carry forward the lessons of the legacy-workspace orchestrator, not its code.

3.2

The eval set is the new spec

Old practice
Unit tests verify code. Humans verify behaviour by using the product.
What changed
The system's main output is agent behaviour, and nothing measures it.
Evidence
No outcome label exists in any store: Hermes, Codex or Claude Code. The reviewer never reviewed a real diff. Codex success labels are graded by the same model that did the work. criteria.json holds one criterion, and it is a placeholder. verified
New practice
No incident, no rule, so no incident, no eval. Each rule's Prevents: incident becomes a planted mistake in a sandbox project, and the reviewer must catch it. Enforce with: already says how.

3.3

Pay human attention once, then gate

Old practice
Review each change carefully.
What changed
Agents produce changes faster than a human can read them. Spend attention on building checks, not on repeating them.
Evidence
Twenty closed MTBT efforts, zero harvested, even after the rule was written three times. verified The comment rule was gamed through a judgement call. A dependency bump passed an existing rule, because rules only fire at review time.
New practice
Anything that matters becomes a deterministic check that runs every time. Keep LLM judgement for what no check can express, and label it as judgement.
Tickets 010811
3.4

Copy instead of share

This is DHH's choke-point argument, and your system shows it clearly.

Old practice
One shared configuration that everybody uses, so nothing is duplicated.
What changed
Copies are free. Shared mutable state is where parallel agents collide and drift.
Evidence
Both worker profiles hard-code one client's Docker image and volumes. Both have memory on and carry client memories unrelated to their role. The three live profiles share one SOUL.md, and it is not the canonical one. Skills reach profiles through persistent global symlinks, which conflicts with per-run bundles. The reviewer's "read-only" mount was writable: its own write probe succeeded 4 times out of 4. verified
New practice
Each run gets its own bundle, its own container, and for the reviewer, its own disposable copy of the work. A hash before and after proves the reviewer changed nothing, and the reviewer can still run tests. Keep the declarations single: that is DRY for knowledge. Per-run copies only duplicate shape, and shape is free.
Tickets 030708
3.5

Pointers checked by machine

Old practice
Docs rot, so humans keep few of them.
What changed
Docs are now input to agents. A broken pointer is a bug in the program, not a typo.
Evidence
AGENTS.md points at three paths that do not exist, and agents rediscovered this in at least four sessions. The tier model appears in three places. code-review still describes a clone-scoped third tier and a removed ./preflight. to-spec says both "do not publish externally" and "publish to the issue tracker". verified In legacy-workspace, a Spanish copy of six rules already contradicted the original.
New practice
State each fact once, point to it everywhere else, and let a pre-commit check prove that every pointer resolves.
Tickets 0102
3.6

The spec is the expensive artifact

Old practice
A spec is a rough guide. The developer fills the gaps while coding.
What changed
An agent fills gaps at machine speed, confidently, in the wrong direction.
Evidence
The INST-142 task pointed agents at a host path while the spec was mounted elsewhere. A board had no default workdir. Skills named in a task were not installed on the profile. None of these were code problems. All of them were unstated assumptions in the task.
New practice
A ticket is a contract that the orchestrator validates before it spends a token. Every acceptance criterion states how it is verified.
Ticket 04
3.7

Control flow must terminate

Old practice
Retries and requeues are free, so be generous.
What changed
An unattended agent loop has no natural end, and nobody watches it.
Evidence
Kanban task t_ed81287a has logged 1,237 respawns since 2026-09-22 and was still running. Rate-limit and auth requeues do not count as failures, so no breaker trips. verified One Codex session burned 26.5M tokens from one prompt. /goal budgets were used once in about 900 prompts.
New practice
Every run ends in exactly one labelled final state, within time and token budgets that the orchestrator enforces, not the agent.
Ticket 09
3.8

The trace is the product

Old practice
Logs exist for debugging.
What changed
When an agent does the work, the trace is the only thing a human can verify.
Evidence
Worker sessions record $0 cost because of subscription billing. Rate-limit errors were shown as "Authorization error" and became the title of 18 sessions. No task links to the commit it produced.
New practice
One structured record per run: ticket, clone, base and head commits, bundle manifest, model per role, tokens, duration, final state, findings tagged with rule ids, and the human verdict. Start with a JSON Lines file. Move to OpenTelemetry once you know which questions you ask.
Tickets 0610
3.9

The learning loop is a gate, and its input must shrink

Old practice
People remember to write down lessons.
What changed
Nobody remembers, and agents over-generalize. The README already decides that humans own this loop.
Evidence
Zero harvests out of twenty. The memory queue holds 10 memory and 21 skill requests against a placeholder criterion. verified One pending proposal would record where a QA password is stored.
New practice
Closing a run takes one human pass with three jobs: verdict (the outcome label), harvest (zero is normal), and next action. Shrink the input instead of building a better reviewer for it: worker profiles learn only through approved bundles, never through autonomous memory.
Tickets 0311

4How to keep finding revaluations

  1. For any practice, ask what cost it paid down, and whether that cost moved.
  2. Let the run history be your friction log. Every run ends in a labelled state with a one-line human note. Each week, group runs by final state and by rule id, and turn the top category into a ticket. This answers the README's fourth problem: how the system improves over time.
  3. Tag each rule and decision with the cost it pays down. When models get cheaper, contexts grow, or a check becomes automatable, revisit exactly the rules tagged with that cost.
  4. Treat a re-derivation as a finding. The orchestrator was designed twice because nothing indexed what already existed.

5Risks not ticketed yet

  • Parallel runs share state outside the worktree: dev database, ports, the sqlserver_default network, git identity. Decide a policy before two tickets run at once.
  • Provider limits (429, 402, 403 across Copilot, OpenRouter and OpenCode) caused the most failed runs. A run must fail fast as infra_blocked or provider_error, never requeue silently.
  • Security-scanner false positives ("Nested executable body could not be resolved") appear in both worker profiles, and the logs cannot tell them from real blocks.
  • Text-only review misses rendering bugs. The bootstrap duplicated-row bug surfaced only when real terminal output was pasted.
  • Model routing is manual by decision. The run record must at least store which model each role used.
  • Vendored skills without provenance. grill-me, to-spec, tdd, triage, codebase-design and diagnosing-bugs come from an upstream collection with no recorded version.
